# Executor Work Continuity

Date: 2026-09-12

## Contract and scope

Work retained by a successfully acknowledged command must be recoverable. An interrupted command must explicitly report that it may have partially completed.

Acknowledgement is distinct from exit code zero or a successful remote save. A normal command result with a nonzero exit code still covers its retained local work; recovery must not discard it merely because the command reported failure.

This proposal changes the disposable-session lifecycle described by [CodeAct content and media](../implemented/2026-09-09-codeact-content-and-media.md) and the [worker reference](../../executor-service/README.md). It does not change remote Git authority: retained local edits are neither a save nor publication. Until the implementation and its failure tests land, expiry and restart can still discard unsaved work.

The broader [CodeAct workspace proposal](2026-09-09-codeact-workspaces.md) retains its tooling and isolation scope. [Session artifacts](../implemented/2026-09-10-session-artifacts.md) retain their separate access, expiry and byte-delivery contract. Neither record is retired by this proposal. [Multi-user workspaces](2026-09-11-multiuser-workspaces-and-discovery.md) retain membership, public authoring and discovery decisions.

The [working-copy identity gate](../implemented/2026-09-12-executor-copy-identity.md) implements explicit admission and pre-execution rejection. Durable recovery and the remaining resource changes below remain proposed.

## Problem

An MCP transport session can expire during a long conversation. Reconnection creates another executor copy at the same repository commit. A commit therefore cannot identify a working copy or establish that local edits survived. Network loss, application deployment and worker restart create similar ambiguity. Current session and command admission bounds protect resource use but do not preserve a user's work or distinguish capacity rejection from lost execution state.

## Working-copy identity

Expose an opaque working-copy ID independently of the MCP transport session and pinned Git commit. Mutating and read commands that continue a copy carry its expected ID. Resolve current authorization and compare that ID before starting the command or applying a host operation. A missing, replaced or inaccessible expected copy must not silently create a substitute and run the command: return `SESSION_REPLACED` without executing it, with an authorized recovery or explicit new-copy path. Do not disclose other identities' copies.

Initial admission must identify the new copy before dependent work. Subsequent responses expose its ID and execution outcome. A response-only `fresh` flag is insufficient because the command could already have written into an unintended copy. Client guidance must retain the ID across tool calls; tests must exercise the actual MCP schema and handler rather than only a Java entry point.

Recovery is explicit and bound to the original subject, workspace and currently permitted scope. Never auto-claim by subject and workspace alone: two chats using one identity own independent copies. A copy has one fenced writer lease. A stale transport or worker cannot continue writing after ownership transfers; simultaneous recovery attempts cannot both win. Permission revocation or public-projection withdrawal denies access immediately, regardless of retained bytes.

Explicit recovery and execution must be possible in one admitted request. A client may open a new MCP transport for each tool call, so a separate resume call cannot require that the next command reuse its transport. A recovery request identifies the exact copy and expected writer generation, transfers ownership atomically, and fences the previous owner before executing. A stale generation is refused before execution. Transport replacement never authorizes a fresh copy or an identity-wide automatic claim.

## Durable retained work

Use a durable working directory, or an atomically published recovery checkpoint at command completion. A success response follows durable publication of the retained state. Exit cleanup cannot provide the guarantee: abrupt termination may bypass it. Failed persistence returns an explicit failure rather than acknowledging recoverable work.

Keep the last complete worker checkpoint and its host save state separate from any unconfirmed command state. Host records bind the subject, workspace, copy, fixed read scope, transport, record revision, writer generation and visible expiry. Publish bounded checksummed records through a private application-owned directory, file fsync, atomic replacement and directory fsync. Reserve space for both the old record and its temporary replacement; quota or encoding failure must leave the old record intact. Cross-process exclusion and revision checks protect metadata updates, but do not stop a worker: the recovery coordinator must separately confirm containment before transferring execution ownership.

The worker's [checkpoint protocol](../../executor-service/README.md#worker-checkpoints) supplies immutable host files and explicit source-lease containment. It retains the trusted original export separately from mutable Git state, verifies complete bytes before extraction and requires a fresh restore lease. Configured retained execution invokes command-boundary persistence and exposes explicit copy/generation recovery with execution in one MCP request. Retention remains disabled by default. Native crash-window and authenticated model-client evidence are recorded below. Final HTTPS acceptance and the resource/admission work remain pending; this proposal is not yet fully delivered.

Recovery holds the writer lock while confirming that the latest recorded lease is closed, then publishes its new generation and writer identity before RESTORE. The record includes the prior application boot ID: a new application process may use it only to sign a containment request, never to start work under the old identity. An unconfirmed close keeps the lock held and blocks transfer; a new worker boot proves startup cleanup. Recovery selects an interrupted command's paired checkpoint when present and otherwise selects the last acknowledged point. The previous acknowledgement remains separate until the recovered command completes. Admission refusals describe only the new request; the prior interrupted command ID remains visible after successful recovery.

Fixed expiry is enforced independently of MCP idle. The application closes an expired active lease and collects expired, checksummed host records only while it can hold their writer lock. Collection uses a separate thread from lease renewal and reads a small expiry projection rather than constructing the saved work state. The worker independently collects expired checkpoints and unpublished temporary files under its checkpoint lock; private ownership, header identity and filename checks precede deletion. Both collectors run periodically without client requests. Contention defers cleanup, and malformed or aliased entries are retained rather than treated as expired. Copy and disk quotas still bound retained storage; expiry collection does not provide fair admission or reserve room for a future command.

The application coordinator must hold a per-copy cross-process writer lock for the entire admitted command, including host writes, metadata publication and recovery. Reload and compare the expected generation after acquiring that lock. A record update around the candidate-commit callback alone is insufficient: an old application thread could still push after that callback while another process takes ownership. A busy writer therefore prevents transfer until it finishes; application process loss releases the OS lock. Before starting a worker command, retain the current worker boot and lease ID alongside its intent. Recovery must contain that latest writer as well as the last checkpoint's source lease, because an interrupted restored command can have a newer lease without a completed checkpoint.

Host records carry the latest worker and application boot IDs and lease; changing any of them requires a new generation. The metadata store supplies bounded per-copy writer locks independently of its short metadata lock. Every lock acquisition first excludes same-JVM contenders before opening a channel: on Linux, closing a competing channel can release the original process lock, as described by the [Java file-lock contract](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/nio/channels/FileLock.html). Writer files are never removed while held. Unowned files without a record are reclaimed only under the metadata lock that also guards writer acquisition, so a new holder cannot open a replacement inode while a contender still targets the old one. Retained command admission acquires this lock before opening a worker copy, reloads the expected record revision and generation, and holds it through acknowledgement. Failed execution keeps the lock until worker containment is confirmed. A failed close-attempt future does not establish containment: the lock follows a separate signal completed only when worker admission is safely released.

An unconfirmed command retains its own paired worker checkpoint and host state, separately from the last acknowledged command. `CHECKPOINT_ACTIVE` captures a running command with its cgroup frozen and returns RUNNING with the matching execution ID. Retained commands use these intermediate points at host-effect boundaries: preserve pending write payload and the exact candidate before pushing, then pair completed save, sync, move or import state with matching worker bytes before returning its bridge reply. A successful save inside an interrupted command must not restore an older file under the saved file's newer baseline. Initial admission captures READY state before command intent; completion publishes a new READY point before returning any normal result, including a nonzero exit. Only after metadata publication are superseded worker points removed. Failed publication preserves the previous point; uncertain or failed cleanup requires later collection.

Selected-file save and recovery accept a host-state persistence callback through their session state. Tracked saves retain the selected patch before entering the repository writer, then retain its exact candidate through the writer's pre-push barrier. Completion builds a prospective state with updated selected-path baselines and the save receipt; that state replaces the live state only after persistence succeeds. A completion failure therefore leaves the candidate available for reconciliation rather than acknowledging an unretained baseline. Tracked recovery with no retained candidate can clear an unstarted intent without writing; a committed candidate is reconciled without a duplicate push. Synchronization likewise persists its prospective per-path baseline before adopting it. Executor session construction binds these callbacks in retained mode; ephemeral execution keeps its untracked writer path.

Completed tracked saves retain the exact acknowledged patch text or deletion alongside each selected path's commit. Synchronization retains the remote source used by its merge, separately from the merged local text. These immutable values travel with the paired host checkpoint, so later save and sync operations need no historical cache read for those paths. Reads still require current private-read authorization, and writes retain the shared writer's remote-base and revision checks. Record validation binds each value to its tracked path commit and applies the existing text byte limit; the complete serialized metadata remains subject to the configured record and aggregate storage quotas. Paths still pinned to the original commit use the immutable original archive. Advanced paths carry their acknowledged file versions; missing retained versions fail rather than querying historical cache data.

Moves retain the complete local installation plan before entering the remote writer, its candidate before push, and the confirmed remote result before reporting a pending local installation. Installed and skipped outcomes persist their prospective state before changing live baselines or clearing the plan. The session owns independent copies of pending plans; the executor reads the current session-owned result after commit rather than relying on a caller's mutable plan object. Completion checkpoint failures leave the prior recoverable intent intact, including when their exception resembles a repository or authorization error: only exceptions from the remote write itself are classified as remote failures. Retained execution binds these callbacks to paired worker and host checkpoints.

Tracked moves also read each affected path's text or absence at the acknowledged remote commit and retain it with the confirmed plan before local installation. A failed read leaves the exact candidate available for reconciliation without repeating an acknowledged push. The retained media index comes from remote Git, not the local installation payload, which may contain unselected draft mappings. Successful installation adopts those versions together with the affected path commits; skipping local installation preserves the previous versions. Non-text entries are not represented as absent text.

Moved file baselines distinguish text, non-text presence and absence explicitly. A non-text version retains its optional exact-byte revision, diagnostics and read scope, including indexed media without a text revision. Capturing a file verifies its workspace, path, commit and source revision; persisted diagnostics must belong to that path. Private retained checkpoints require a version for every advanced path and, for a confirmed pending move, every affected path. Incomplete state cannot be acknowledged. Metadata frame and aggregate storage quotas cover these values, including diagnostics. Text saves reject non-text existing targets before retaining a write intent; preserving their presence does not make them writable through the text interface.

Import receipts share that host-state snapshot. After the managed store acknowledges an upload, the executor retains its exact receipt before releasing capture staging or attempting index installation. Linking an existing managed original retains its receipt before installation too. A second callback pairs the updated index with an indexed receipt before reporting success; a failed callback leaves the prior live receipt intact. Import receipts remain presentation data, not authority to repeat an upload or write Git. Retained execution binds both callbacks to worker and host checkpoints.

Public-copy records retain the original host-only publication fingerprint, authority commit and path/media mapping alongside the pinned projection commit. Record validation prevents a missing proof, another workspace or another baseline from being substituted. Restoration must install this proof before authorizing output and revalidate it against current publication; persisted metadata does not itself authorize continued public access.

The [native worker lifecycle evidence](../../executor-native/evidence/2026-09-13-retained-worker-lifecycle.json) verifies private draft text and binary bytes after an actual supervisor kill and restart, preserving the original commit and archive reference. Public recovery preserves its projection and local draft while excluding private files and history even after a permission increase. Private-read denial and publication withdrawal reject recovery before changing metadata. These checks use synthetic authorization; separate evidence below covers real-account client recovery and application crash windows.

Retain the original pinned commit and its required Git objects, worktree contents including untracked and binary files, the media index, independent per-file save baselines, and pending save/move receipts needed to reconcile unknown remote outcomes. Restore these together to the same baseline; do not reconstruct them against current remote `main`. Existing save/sync/recover conflict checks handle a remote that has advanced. Do not add a recovery-specific merge algorithm or automatically retry an uncertain remote write.

Original-baseline ingestion uses bounded private traversal on `AuthorizedRepositoryReader`. It resolves one pinned commit in one authoritative read and streams Git entries, including directories, followed by indexed-media paths not already present in Git. Individual queries and traversal share the same file decoder, preserving text revisions, unreadable files and managed-media diagnostics without following links or fetching original media. Entry count, aggregate UTF-8 source bytes and elapsed traversal time are bounded; the destination separately bounds its encoded data. Invalid or unrepresentable paths fail traversal rather than becoming aliases. Current private-read permission is checked before traversal and again before completion. The sink stages private data and discards it on failure; it must not infer absence or publish that data before successful completion.

The original-baseline archive codec stores each `RepositoryFile` in an independently compressed frame. A fixed-width index, ordered by the SHA-256 of exact UTF-8 paths, provides lookup without retaining the complete original source table in memory. A separately checksummed header binds subject, workspace, copy, original commit and expiry; the expected reference also binds archive length, entry count and the complete-file SHA-256. Opening verifies that reference through one file descriptor, validates index order and exact frame coverage, and retains only the index and one bounded decoded entry at a time. Source revisions and file identities are checked on write and read. Missing paths are reported only from a verified complete archive. A failed row poisons the writer even if its producer catches the sink error, and the valid header is written and fsynced only after the producer returns successfully. Encoded archive bytes, aggregate expanded bytes, per-entry expansion and entry count have independent bounds, including header and index overhead. Each open scans the complete archive for integrity; consumers should reuse an open reader within an admitted operation rather than repeat that scan per selected path.

The original-baseline store provisions a separate private persistent directory, validates ownership and file aliases, and bounds archive count, aggregate bytes and available disk space. Capture holds the copy writer and a separate nonblocking archive lock; source traversal does not hold the metadata lock. Publication uses a new private file, file fsync, atomic rename and directory fsync. A failure after rename reports an uncertain outcome. Reads bind the archive identity to the live copy record and require the same writer lock throughout lookup. Current authorization remains the caller's responsibility.

Independent periodic collection removes expired or unacknowledged archives only after acquiring their exact copy writer under metadata exclusion. An active writer defers removal, including one held by another JVM. Maintenance can acquire an orphan writer at ordinary admission capacity, so a full writer quota does not prevent reclamation. Malformed or aliased entries are preserved and reported. Enabling retention provisions metadata and original-baseline stores together in separate persistent roots.

Private-copy admission captures the original archive after worker OPEN, at that worker's pinned commit and before the initial checkpoint or EXEC. The archive and record share one fixed expiry. The record contains the immutable reference once; validation binds owner, workspace, copy, commit and expiry, and metadata replacement preserves the complete reference across writer generations. Public copies cannot contain a private original reference. Source failure prevents the initial worker checkpoint; checkpoint or metadata failure leaves an unacknowledged archive for collection after writer release. Existing and resumed copies reuse the recorded reference without traversing remote history again. Store reads require the exact reference in metadata. Executor baseline lookup now uses that archive for paths still pinned to the original commit. Advanced versions are retained separately with their host checkpoint.

Each admitted private command binds its save state to an original lookup under that command's writer. State copies preserve the binding, and the next command or recovery binds a fresh lookup. The first original query verifies and opens the archive; later queries reuse that reader until the command releases it, before releasing its writer lock. Permission is checked before reading and again before returning the result, without holding an authorization transaction over archive I/O. Lookups also bind the subject, workspace and original commit, and an opened reader still checks writer validity and expiry. Missing paths become known absence only through a verified complete archive. Missing or corrupt archives never trigger a historical-reader fallback or substitute mutable worker files. Existing remote-base and revision checks still reject conflicting writes; synchronization reads current remote input separately.

Persist command intent before execution and distinguish acknowledged completion from an interrupted or unconfirmed result. On recovery, an incomplete command reports possible partial local changes and any uncertain host write. Never infer failure solely from a missing response or claim a command did not execute. Host write reconciliation remains authoritative even when a process dies between a remote commit and its local acknowledgement.

The [native JVM process-loss evidence](../../executor-native/evidence/2026-09-13-retained-jvm-process-loss.json) externally kills the application after an acknowledged command and during a command with an acknowledged host save. Independent recovery JVMs retain the original commit, draft text and binary bytes, original archive, per-file baselines and save receipts. The worker boot is unchanged, the application boot changes, and the interrupted command remains identified. A restored draft can then be saved and read back from authoritative Git. These checks use synthetic authorization; other persistence/push/response crash windows and real-account/client acceptance remain pending.

The [post-push process-loss evidence](../../executor-native/evidence/2026-09-13-retained-push-process-loss.json) kills the application after the real remote ref advances and before the host writer receives acknowledgement. A new JVM restores the original candidate and pending write; explicit `poketto recover` confirms that candidate without another push, clears uncertainty and retains its saved content. All three focused process-loss cases and cleanup pass. Command-acknowledgement publication boundaries and real-account/client acceptance remain pending; these tests use synthetic authorization.

The [publication-boundary evidence](../../executor-native/evidence/2026-09-13-retained-publication-process-loss.json) kills the application before final command metadata replacement and after its file/directory synchronization but before response delivery. Recovery before publication preserves the prior acknowledged draft and interrupted-command identity; recovery after publication preserves the completed draft whose response was lost. Both can subsequently be saved. All five focused process-loss cases and cleanup pass with synthetic authorization. These process tests do not establish host power-loss durability; real-account client coverage is recorded separately.

The [retained HTTP evidence](../../acceptance/clients/evidence/2026-09-13-retained-http.json) exercises real Spring authentication, PostgreSQL and SRT through an independent HTTP MCP client. Every tool call replaces its transport. Private drafts and binary bytes recover at their original commit; stale generations cannot execute, other key subjects cannot take over or discard a copy, and recovered drafts save with authoritative HTTP readback. Public copies remain public-only after recovery. Discard is idempotent without undoing Git, and revoked keys cannot initialize another session. All five checks and fixture cleanup pass.

The [retained model-client evidence](../../acceptance/clients/evidence/2026-09-14-retained-models.json) exercises actual Codex and Claude Code processes against the authenticated Spring/PostgreSQL/SRT fixture. Each client creates unsaved text and binary files, exits and uses a separate process to resume the exact copy with its expected generation. Both preserve the pinned commit and bytes, save only the selected text, discard the retained work, receive `ABSENT` on repeated discard and receive `MISSING_COPY` on later recovery. Independent transcripts, HTTP readback and remote Git verify exactly two selected-file commits, no binary scratch files and successful fixture cleanup. Client command corrections and the fixture's missing root guidance are recorded. Final deployed HTTPS and chat-app OAuth acceptance remain pending.

The repository writer must invoke a synchronous host checkpoint after preparing and authorizing the exact candidate commit, before closing publication or advancing remote Git. The caller first retains the patch or move and its baseline; the checkpoint adds the candidate commit bytes to that intent. A checkpoint failure prevents the push. Retrying an uncommitted retained attempt uses the same barrier; reconciliation of an already committed attempt and unchanged content require no new checkpoint or push. An untracked browser write does not acquire a retained-work guarantee through this interface alone.

Retained work has explicit byte and retention bounds, owner-visible expiry, and an explicit discard operation. Admission reserves storage before accepting work; quota exhaustion must preserve the last acknowledged recovery point. Unavailable or corrupt retained state fails visibly. Retention expiry and authorized deletion are stated exceptions to recovery, not silent replacement. Temporary process files remain disposable; artifact handles keep their independently documented lifetime.

`repo_discard` takes an exact `expectedCopyId` and `expectedGeneration`, independently of the current MCP transport. It requires current `EXECUTE_REPOSITORY` authorization and addresses only the authenticated subject's workspace-bound record. It returns no retained content, so loss of private-read permission or withdrawal of publication does not prevent owner cleanup; revoked execution credentials still fail authorization. This separate lifecycle entrance can discard expired or inaccessible work without first recovering it or running a command inside it.

Discard holds the exact copy writer, rereads its generation, confirms containment of the latest recorded lease and retires cached sessions. Busy or stale writers refuse deletion. The owner is reauthorized before deleting and synchronizing metadata; worker checkpoint removal follows as best-effort cleanup, and the original archive collector reclaims the orphan after writer release. Failed containment preserves metadata and holds the writer until containment is independently confirmed. `DISCARDED` and `ABSENT` are idempotent outcomes for the requested owner and ID. An unconfirmed deletion may already have removed metadata; its response must not claim that no mutation executed or that work remains recoverable. Retrying the same ID and generation is safe. Discard never reverses remote Git writes, including writes whose receipts were still uncertain.

The [native discard evidence](../../executor-native/evidence/2026-09-13-retained-discard.json) verifies stale/busy rejection, retained metadata and writer exclusion through lost CLOSE replies, successful retry and subsequent `ABSENT`, recovery refusal and preservation of remote saves. Synthetic private-read denial and publication withdrawal still permit owner cleanup. Separate Linux tests cover expired deletion, wrong-owner addressing and invalid containment; MCP tests verify bounded inputs and revocation denial. These results do not establish actual-client acceptance.

## Resource and admission changes

Move retained work off aggregate tmpfs into quota-controlled disk storage, leaving temporary command files bounded and disposable. Reserve host disk headroom and bound I/O as well as bytes. Apply resource accounting to each copy from its creation; moving a process into another cgroup does not transfer memory charged while populating its files.

Timeout and command resource exhaustion terminate the command group and preserve recoverable state when the worker can verify containment and storage integrity. Worker or pool failure follows the interrupted-command contract; it cannot report an intact live copy without verification. Cancellation stops execution; credential revocation additionally prevents recovery access. Cleanup must not erase the last acknowledged retained work as a side effect of releasing runtime capacity.

Use bounded, fair waiting with per-workspace or principal limits and a global resource ceiling. Cold copy preparation and warm commands need separate admission so bundle creation does not monopolize interactive execution. Capacity errors include stable reasons and bounded retry guidance. Idle runtime capacity can be released while durable work remains recoverable; never evict unsaved work merely to admit another client.

Reuse immutable export bundles by workspace, pinned commit, full/public view and projection version, with bounded storage, single-flight creation and active-reader lifetime protection. Revalidate scope and publication. Never share writable Git object inodes or authorize a public copy with a full-history cache entry.

## Delivery and acceptance

1. **Detect replacement before execution.** Add expected-copy identity, explicit initial admission and mismatch behavior, plus active-copy, admission/refusal and lifecycle metrics. Test transparent reconnection at an unchanged commit with unsaved content, two parallel chats under one identity, wrong-scope IDs, and a rejected command that provably did not execute. Until durable recovery ships, report lost/unavailable copies honestly.
2. **Preserve acknowledged work.** Implement retention and fenced recovery. Exercise idle expiry, network loss, application deployment, worker termination and interrupted commands on native Linux. Verify original commit, untracked binary bytes, independent file baselines and uncertain-write receipts after recovery. Advance remote Git before recovery and prove that existing conflict handling is used. Kill the process before and after persistence/response boundaries; test full disk, checkpoint failure, revoked access and concurrent recovery.
3. **Make capacity usable.** Add disk quotas, per-copy resource containment, fair admission and bundle reuse. Measure memory, disk, queue age, rejected admissions, command duration and recovery outcomes without content, credentials or unbounded identity labels. Verify that one saturated copy cannot erase another's acknowledged work; burst reconnections must remain bounded and provide a determinate outcome.
4. **Strengthen and measure isolation.** Validate independent OS identities with persistent ownership and UID reuse accounted for. Extend cross-copy access tests through recovery and identity reuse. Measure warm-command and cold-copy cost before adopting persistent sandboxes or a different history protocol. Existing export byte, object, commit and time bounds remain in force.

An independent refinement change can add `poketto media link`, bounded error reasons, an optional 64 KiB artifact page limit in both schema and runtime, and tool descriptions for command cwd and temporary-directory reset. These do not depend on durable recovery and must not claim it is delivered.

## Alternatives and consequences

Increasing the global session count alone postpones rejection and raises resource consumption. Shorter idle expiry alone increases work loss. Automatically sharing one copy per identity and workspace couples unrelated chats. Packing a diff only during normal shutdown misses crashes, untracked binaries and host-write recovery state. Restoring onto current remote history changes the user's baseline and creates an implicit merge. These alternatives do not satisfy the contract.

Durable local work adds storage ownership, retention and recovery complexity. It is not an off-host backup guarantee, and independent executor hosting remains a deployment option rather than a prerequisite for the first two steps. Dynamic users require an ownership and UID-reuse design; enabling `DynamicUser` independently for each command is insufficient. Keep the existing deny-by-default sandbox boundary and measure any additional layer with real cross-session probes.
