# OAuth for MCP clients

Date: 2026-09-11

## Problem and decision

Browser-hosted MCP clients cannot all supply a manually configured API-key header. Add a standard authorization-code entrance to the existing password account and workspace-key boundary. Users sign in on Poketto, explicitly choose the requested permissions, and return to their MCP client. A login alone never approves a connection.

This adds MCP OAuth to the [phase-one scope](../proposed/2026-09-05-phase-one-daily-use.md). It does not add social login, consumer signup or additional workspace provisioning. The [identity requirements](../implemented/2026-08-25-requirements-and-architecture.md) remain authoritative for memberships, capabilities and data isolation. Existing static keys remain available.

## Protocol and authority

Configure `POKETTO_OAUTH_ISSUER` as the public HTTPS origin without a trailing slash; the shipped Compose profile derives it from `POKETTO_PUBLIC_DOMAIN`. Publish authorization-server and protected-resource discovery, including the exact `/mcp` resource, authorization-code and refresh grants, `S256` PKCE, public-client authentication, and issuer identification in authorization responses. The gateway routes these discovery documents to the backend. The issuer comes from operator configuration, never a request Host header.

Support dynamic client registration with bounded names and exact HTTPS callback URIs; registration does not authorize access. Client names are self-reported and the consent page displays the return URI. No client-provided URL is fetched. CIMD, confidential clients, implicit grants and client-credentials grants are outside this entrance. Claude and ChatGPT can use DCR with public-client PKCE; each actual client still requires a separate interoperability run.

Session cookies use `SameSite=Lax` so top-level OAuth navigation preserves the browser session. This applies to all cross-site top-level GET navigation, not only OAuth; GET routes must not change account authority or content. Unsafe requests still require CSRF proofs and allowed origins. Authorization requests expire after ten minutes and belong to the initiating browser session. Login rotates the session ID while retaining the pending request. The owner must explicitly approve a subset of the requested scopes. Private reading, private writing and publication start unchecked. Key management cannot be delegated through OAuth. Only current workspace owners may create connections, matching the existing key-issuance policy.

Each approved connection owns a distinct backing workspace key. Opaque authorization codes and access/refresh tokens are stored only as SHA-256 digests. Codes expire after five minutes, are single-use, and bind client, exact redirect, resource and PKCE challenge. Access tokens last at most ten minutes; optional refresh tokens rotate on use and last at most thirty days, bounded by the connection's ninety-day lifetime. A refresh without `resource` retains its stored audience. Changing or disabling the configured issuer invalidates OAuth access through the existing authorization boundary.

Refreshing cannot expand permissions. A proven code or refresh-token replay revokes the entire connection in a committed transaction before returning an error. Workspace row locks serialize issuance and replay with existing membership and key revocation. The normal authorization checks still run on every operation. Revocation uses existing events to close affected execution sessions. Other connections remain independent.

Browser consent and disconnection retain CSRF protection. Only registration, token exchange and token revocation are exempt; these endpoints authenticate protocol proofs rather than browser sessions. Auth bodies retain the 16 KiB limit. Registration and token endpoints have bounded per-address admission; registration has a global 4096-client ceiling and each workspace permits at most 100 active connections. Expired transient tokens are cleaned during issuance. Unconnected registrations have a fixed twenty-four-hour lifetime, which anonymous requests cannot extend. Pending consent for these registrations expires no later than that deadline. Connections retain their client registration; connections revoked or expired for over thirty days are reclaimed with their backing keys and tokens when registering or approving a connection. Unreferenced expired registrations are then removed, except the client receiving current human consent. A reclaimed client must register again. Final consent and registry cleanup serialize on the same database advisory lock; contention fails immediately. Workspace and token lock waits are capped at two seconds, with five-second OAuth transactions. Lock contention or transient database timeouts return `temporarily_unavailable`; a consent request remains available for retry. OAuth backing keys appear only in the application-connection list, separate from static API keys. The global cap can still reject new registrations during sustained admission pressure.

## Alternatives and consequences

[Workspace routing](2026-09-11-workspace-browser-and-mcp-routing.md) supplies account-independent consent loading and explicit space selection. The chosen workspace remains fixed in the connection's backing key.

A static API key in an OAuth client-secret field does not implement OAuth. Query-string credentials expose durable secrets through URLs and are not supported. A separate identity provider would add an operational system while still requiring a bridge to Poketto's current membership and revocation model. The selected entrance keeps opaque tokens and durable state beside the existing identity tables; it takes responsibility for a deliberately limited OAuth protocol surface and its concurrency tests.

The backend's connection list and consent page are shared across clients. Connection state survives application restarts; incomplete browser authorization requests do not, so those must restart from the client. Owners can disconnect applications without exposing their tokens. The list prioritizes currently usable connections so revoked history cannot hide a revocation target; connections for a previous issuer are labeled as needing new authorization and do not consume the current issuer connection quota. A disconnected application must obtain new human consent.

## Verification

PostgreSQL and HTTP integration tests cover real PostgreSQL transactions; discovery and login through the Spring security chain; CSRF; invalid callbacks and duplicate parameters; PKCE, client and audience binding; code and refresh replay; expiration; reduced scopes; and independent revocation. Browser acceptance exercises login, consent and connection removal through the built application. Deployment must preserve existing accounts, keys, content and originals. Synthetic protocol/browser evidence and successful actual Claude/ChatGPT connections are reported separately.

The browser fixture, deployment and actual external-client results are recorded separately from these automated protocol tests.
