# Repository Authoring Foundations

Date: 2026-09-05
Status: Implemented

## Scope

This record owns repository-native reads, the public content snapshot and its format bounds, the atomic text writer, managed originals and snapshot-bound image delivery of the [phase-one delivery](2026-09-05-phase-one-daily-use.md). The [identity HTTP backend](2026-09-06-workspace-identity-http.md) owns accounts, invitations, membership, keys and browser sessions; [member content permissions](2026-09-12-member-content-permissions.md) own which capability each changed path needs; the [MCP and local execution record](2026-09-05-local-execution-supervisor.md) owns the transport and worker adapter.

## Repository and publication

`RepositoryContentReader` reads exact UTF-8 blobs and service-issued revisions from arbitrary paths. Explicit commits must be full lowercase Git object ids reachable from current remote `main`. Missing files return expected absence; existing unreadable files return diagnostics. Structured Markdown accepts optional frontmatter, preserves original source, falls back to a real Markdown heading or filename for title, and uses path-filtered Git history for missing dates. Malformed files and path/route collisions are isolated. Traversal, Git internals, symlinks, and submodules cannot supply structured documents.

The authority's object-only read path fetches history and updates the local ref without a checkout or the legacy `documents/` validation gate. Tree scans cap entries at 100,000.

`ContentLimits` fixes the content format's resource bounds as constants; content beyond them is invalid, not a configuration matter.

| Bound | Value |
|---|---|
| File bytes (exact blob) | 1 MiB |
| Frontmatter bytes (UTF-8, between the delimiters) | 16 KiB |
| Title length (code points, after trimming) | 200 |
| Tags per document | 32 |
| Tag length (code points, after trimming) | 64 |
| Repository path length (characters) | 255 |
| Markdown files per workspace | 10 000 |
| Markdown bytes per workspace | 256 MiB |

A file beyond a per-file bound is diagnosed and excluded from structured results. A tree beyond the Markdown count or byte bound fails the scan as a repository-level error. The writer measures each candidate tree against the same count and byte bounds and refuses a patch that would exceed them, so the remote never receives a tree the scan rejects for size. Raising a bound is a content-format decision that needs its own record; a repository already beyond one is invalid until reduced. The bounds were chosen for a personal knowledge base on one server and have not been measured against a repository near them; the workspace count and byte refusals of the scan and the writer have no automated test, because reaching them needs a repository at the bounds.

Date inference keeps independent JGit path walks, preserving merge simplification, file-mode changes, deletion and reintroduction at the same path, and the minimum and maximum committer timestamps even when clocks move backward. It does not follow renamed paths.

Each read shares at most 32 MiB of immutable Git objects and 8 MiB of tree-pair differences; ordinary commits whose path is unchanged skip the path-specific tree scan. Missing dates therefore do not charge every document for a fresh scan of every historical tree. Actual work is bounded by 100,000 distinct commits, 10 million path-walk commit visits, 64 MiB of uncached commit reads, 256 MiB of uncached tree reads, and 2 GiB of tree bytes parsed including cache hits. Cache budgets include entry overhead. Exhaustion raises a repository-level error naming the budget in administrator logs; it neither invents dates nor labels documents malformed. Public snapshot installation remains closed on failure. These limits bound work without claiming selective network transfer.

`PublicContentSnapshots` reads a tree and its `.poketto/publishing.yaml` in one authority operation. Missing or disabled policy produces an empty public snapshot. Invalid policy closes public service immediately; a CLOSED marker is written before validating a changed commit. The marker, `poketto-public-snapshot` in the cache's Git directory, records the commit, its verification time and whether publication is open; it disappears with the cache, and the cached objects are enough to rebuild the snapshot from it. On supported production filesystems, marker publication synchronizes the temporary file before atomic replacement, then synchronizes the Git directory, content-cache directory, and its workspace parent before returning. Offline restoration requires a durable-version OPEN marker matching the cache ref and retains the original verification time. Older or Windows-written markers require fresh remote verification. Public reads reject expired snapshots, snapshots dated in the future, and unavailable publication state. The configured lifetime cannot exceed one hour.

Publication policy uses the bounded YAML and glob schema in the phase-one record. Top-level YAML nodes are checked before map construction so merge keys cannot bypass unknown- or duplicate-key rejection. Public path eligibility runs before route collision resolution: a private file cannot suppress or reveal a public article by changing its route metadata.

Public requests never fetch remotely: resolving remote `main` per request put remote latency and outages on every page view and queued concurrent requests behind one fetch. `ContentSnapshotRefresher` runs every `poketto.repository.refresh-seconds` (default 30) and refreshes the default workspace plus the next page of eight published workspaces, rotating through the catalog; refreshing an unchanged commit only renews its verification. A write through Poketto installs its commit immediately; a valid direct push becomes visible when its workspace is next refreshed. A failed refresh keeps the current snapshot until it expires after `poketto.repository.stale-after-seconds` (default 3600, never shorter than the refresh interval). Until then a reader sees the last verified content without an indication of its age. Refreshes and writes share the workspace lock, so a slow fetch can delay a write by up to the transport timeout.

Startup keeps the application and refresh loop running when content is unavailable, so authenticated diagnosis can be integrated without requiring a Git repair before the process starts. The `contentSnapshot` health indicator reports `UP` while the default workspace has a current snapshot and `OUT_OF_SERVICE` otherwise, without contacting the remote; the aggregate `/actuator/health` read by deployment checks includes it. The public endpoints are `GET /api/public/documents` and `GET /api/public/document?route=...`; the former UUID document route is absent. Responses carry commit, verification time, expiry, and `no-store`. Public mappers omit raw frontmatter, revisions, private diagnostics, and source repository paths.

Public and authorized private search perform case-sensitive literal matching with tag and date filters. Query length is capped at 200 characters, tag length at 64, pages at 100 results, and snippets at 240 characters. Tag pages are capped at 200 entries. No database content index is present.

Windows development uses an explicit online-only public-snapshot mode because its directory provider does not support these durability primitives. Fresh remote verification can install an in-memory snapshot, and that running snapshot keeps its normal bounded expiry. A process restart never restores public authorization from disk on Windows, even from a durable-version marker copied from another host. Linux synchronization errors never select this mode. This limitation does not alter the Linux production contract.

## Atomic authoring

`RepositoryPatchService` validates a batch of at most 64 text changes and 4 MiB, with a 1 MiB per-file limit. Every path carries a revision or explicit expected absence and the batch names the exact base commit, including explicit unborn state. An in-memory Git index builds the candidate; untouched objects and file modes must remain identical, including when the index editor would otherwise replace an ancestor or directory implicitly. Moves are checked deletion/creation pairs. Images and non-UTF-8 binary files are not writable through this service.

The base commit must equal remote `main` when the write runs. Any other commit, including one that touches unrelated paths, is a conflict, and the caller re-reads. The candidate is built on the base tree, and its publication decision, required capabilities, media-index validation and path-collision checks read that tree's policy, media index and entries; an unrelated commit can change any of them. Rebasing onto a moved `main` would therefore authorize and validate a tree the caller never read. Per-path revisions and expected absence still verify the bytes the caller replaces. Only recovery of a retained write attempt reconciles against a moved `main`. The cost is that concurrent writers conflict even when they touch different files, which a per-file content-hash check alone would allow.

`AuthService.withAuthorization` holds the workspace row lock through the operation, serializing it with membership and key revocation. A changed path the publication policy permits needs `PUBLISH`; any other changed path needs `WRITE_PRIVATE`, except that creating a Markdown file directly in `private/inbox/` needs only `CAPTURE`, which `WRITE_PRIVATE` implies. A policy edit, a change while the policy is invalid, a changed media entry at a publishable path and a path that becomes publishable also need `PUBLISH`. [Member content permissions](2026-09-12-member-content-permissions.md) own these requirements and those of moves; the [capture inbox](2026-09-24-capture-inbox.md) owns `CAPTURE`. A changed raw body is retained exactly rather than canonicalized.

Commits use the fixed service author and committer `Poketto <poketto@invalid>`, whose reserved domain routes nowhere, and the subject `Apply repository changes`. The acting account or API key appears only as its principal type and opaque UUID in a `Poketto-Principal` trailer; an accepted [reader correction](2026-09-24-reader-corrections.md) may add `Poketto-Suggested-By`. Commit metadata never contains display names, email addresses, credentials or session tokens: content repositories may be mirrored off-host, so Git history carries only durable opaque identifiers. `WritePrincipal` accepts at most 64 characters of `[A-Za-z0-9._-]` starting alphanumerically, which makes email addresses, display names and trailer-breaking newlines unrepresentable; that syntax cannot tell whether a valid token is secret.

Before a patch affecting publication can push, it closes the in-memory public view and persists the CLOSED marker. Failure to persist the marker prevents the push. A known withdrawal therefore cannot leave older public authorization available when recording the acknowledged local ref fails or the process restarts offline. A directory-synchronization failure prevents the push and leaves public memory closed. A failed OPEN publication also attempts a synchronized in-place CLOSED record without replacing the directory entry again; an I/O failure never becomes success. A later verified refresh can reopen service.

Remote exact-ref acknowledgement owns success. Concurrent edits conflict. A lost response is reconciled once by reading remote `main`; unreadable authority or failed local recording after verified remote success produces an explicit indeterminate result requiring a fresh read before retry. An acknowledged patch immediately calls the public snapshot installer under the authority lock without another fetch. If installation fails, public state closes and the result still reports the Git commit with `snapshotUpdated=false`; it does not pretend the remote write failed. A database transaction completion error after the external acknowledgement also requires reconciliation.

Browser repository tree, file, private-search, and atomic-patch endpoints use the shared authorized reader and writer. Authentication bodies are limited to 16 KiB; patch and preview JSON to 6 MiB, with the lower domain text limits still enforced. Multipart uploads allow a 16 MiB file within a 17 MiB request.

## Managed originals and image delivery

`ManagedBlobStore` stores originals outside Git under workspace namespaces. The image upload entrance streams at most 16 MiB plus one detection byte, validates image signatures, structural envelopes and dimension bounds, and returns a random asset identity with an exact SHA-256 revision. Supported previews are PNG, JPEG, GIF, and WebP. A workspace-scoped operation key makes an identical retry return the same reference; different bytes or declared types conflict.

The storage port also accepts opaque originals through `uploadFile`, with a default 128 MiB bound. `poketto.assets.max-file-bytes` can lower the upload bound, including image uploads, without making earlier originals unreadable. Declared media types are validated metadata, never permission for inline rendering. `copyTo` verifies exact length and SHA-256 before streaming through an 8 KiB buffer; caller streams remain open. A failed consumer may receive partial output and must discard its staged destination before retry. Image reads independently enforce the smaller preview bound and image policy. The image-specific browser and MCP upload entrances retain their image limits; [indexed media delivery](2026-09-09-indexed-media-delivery.md) adds bounded raw-original HTTP transfers. The [logical media index](2026-09-09-logical-media-index.md) owns path discovery and atomic index/text saves; the [CodeAct content contract](2026-09-09-codeact-content-and-media.md) owns generalized delivery.

A durable digest index and hard links reuse equal bytes only inside one workspace. Distinct upload operations keep distinct opaque identities and metadata, even when their physical bytes match. Different workspaces share neither identities nor physical files. This avoids cross-workspace existence and permission coupling without giving up local deduplication. Original objects have no public flag; a reference still needs the caller's workspace authorization and delivery grant. Deleting or changing a logical reference does not mutate retained bytes.

File and directory synchronization, atomic directory publication, a synchronized operation ledger, and OS file locks protect acknowledgement and cross-process retries. Reads verify exact version, digest, metadata and image policy. All acknowledged originals are retained. The store rejects symlinks and unsupported durability primitives; Windows providers lacking directory synchronization report unavailability instead of claiming durability.

Original and repository-cache file reads issue underlying reads of at most 8 KiB. The complete bounded image array remains inside its image admission scope. This prevents the JDK file channel from retaining image-sized temporary native buffers on idle request threads; it preserves the original byte limit, sentinel detection, digest checks and immutable stored bytes.

Repository images are read-only Git objects, materialized on demand into a bounded disposable cache. Public image grants are opaque and bind the exact page commit and image version for at most five minutes, never past snapshot expiry. Every replay also requires the currently served snapshot to hold the grant's commit and page, so a snapshot replacement, withdrawal or disabled website invalidates outstanding grants; the [website delivery boundary](2026-09-14-workspace-public-delivery.md) owns that rule. Private image access checks current workspace authorization on every request. Upload success neither writes Git nor makes the image public.

Public rendering captures a validated snapshot, prepares exact images outside the workspace mutex, and enters a final publication check before signing grants. Preparation retains only text, links and image descriptors after releasing each image's memory scope. The final check requires the current route and article from the same commit and uses the current snapshot expiry. It performs source metadata validation and grant admission, without loading or hashing image payloads. A changed commit permits one fresh preparation attempt; two successive changes report temporary unavailability. Each attempt has its own 128 MiB image-work bound, so retry permits at most two bounded attempts. Same-commit verification renewal uses the final snapshot without repeating image preparation. A missing route, invalid policy or expired snapshot cannot sign the captured images.

The publication gate locks an independent snapshot holder for each workspace and rechecks that it remains current before invoking the callback. Replacement and removal acquire that holder's lock and conditionally update the map. Business callbacks never hold a map hash-bin lock, so a blocked callback cannot stall another workspace whose key has the same hash. The gate is independent of the authority mutex held during remote fetches. A pending fetch does not extend or invalidate an already verified snapshot; public pages and missing-route results use that snapshot until expiry or observed withdrawal. Exact-object reads also avoid the fetch mutex. A changed fetched commit closes the old entry before marker persistence and validation, so neither slow marker I/O nor an invalid policy serves the earlier publication decision. Gate callbacks may read immutable source metadata but must not fetch or enter mutable repository operations. Authority fetches and exact-ref writes retain their existing serialization and acknowledgement rules.

Private preview, image inventory and exact image delivery use short authorization transactions before and after preparation. Payload reads and validation run between those transactions, allowing key revocation or membership suspension to commit while a read is blocked. Final authorization is required for private text, paths, diagnostics, bytes and new preview grants. A preparation failure is also preceded by that final authorization check so revocation takes precedence over private error details. Private token reads recheck token identity and expiry after I/O. Download callers retain their admitted response scope through serialization; page preparation retains no image arrays for final signing.

A render reuses an image grant with at least one minute remaining, or one already lasting until the current snapshot's expiry. Otherwise it issues a replacement and retains the earlier token until its original expiry. A snapshot near expiry cannot guarantee a full image lifetime. Repeated rendering therefore avoids unnecessary token allocation without handing a fresh page an almost-expired grant when a longer authorization is available.

The shared in-memory grant table retains at most the configured `poketto.assets.max-grants` entries, defaulting to 2048. Capacity exhaustion omits only images requiring a new grant; the article, approved links and reusable grants remain available. Missing inline mappings render the existing unavailable-image label and alt text, with no request to the authored URL; gallery entries lacking grants are omitted. Rate-limited warnings report the number of omitted authorizations without paths, workspace identifiers or tokens. Expired entries release capacity. Image admission remains constrained by that capacity. Live grants are never evicted to admit new readers, and increasing the table limit is not a substitute for bounded admission.

Image work also shares a process-wide memory admission budget. `poketto.assets.memory-budget-bytes` defaults to 256 MiB. Original-image HTTP downloads and multipart upload validation reserve 128 MiB each; MCP image work reserves 256 MiB. These conservative shares cover bounded originals, immutable copies, validation, base64/JSON/SSE encoding and garbage-collection headroom. They are working-set estimates for the pinned runtime, not a measurement or guarantee of total JVM memory. A request reserves before reading images and holds its share through the actual response write. Slow downloads therefore retain admission until completion or failure. At most 16 callers wait, for at most two seconds, controlled by `memory-max-waiters` and `memory-wait-millis` under the same prefix; exhausted HTTP image work returns 429 with `Retry-After`.

Article rendering, private preview and repository image inventory use zero-wait admission while processing each image outside workspace authorization locks. A failed reservation omits that image mapping or adds the private inventory diagnostic `IMAGE_CAPACITY_UNAVAILABLE`; article text and approved links remain available. Original-image request adapters do not acquire these short inspection reservations again. Admission gauges expose reserved bytes and waiting requests, with a cumulative rejection counter, without workspace identifiers or paths.

MCP passes an explicit image scope through its transport context. Actual tool callbacks and blocking JSON/SSE writes register as producers; neither future cancellation nor servlet completion releases their share while they are still executing. The servlet listener is registered when async handling starts. A transport error or timeout completes the servlet lifecycle, with a failure status if the response is not committed; a partially sent SSE response simply ends. Current HTTP image controllers synchronously return byte arrays, so their filter chain covers production and sending. A future asynchronous HTTP image producer must explicitly join the scope before scheduling work.

`index.md` owns its folder route. [Logical routes](2026-09-06-logical-repository-routes.md) preserve the original names, including spaces, `%`, `?`, and `#`; URI encoding belongs to the transport boundary. An index supplies a non-recursive, filename-sorted gallery of eligible sibling images, excluding images already referenced by the body. Ordinary articles do not add neighboring images. Public media resolution excludes private or policy-excluded paths, including references from an otherwise public article. Preview uses the same Markdown destination and image rules, with private URLs requiring the current session.

Gallery discovery scans only the containing directory, with a 100,000-entry work bound. It excludes normalized body destinations, private or policy-denied paths, reserved paths, non-regular files and unsupported extensions before selecting at most 128 candidates in Java filename order. Only selected candidates need object-size reads. Oversized or invalid images are omitted without scanning further candidates to fill their places. This bounded prefix avoids an unbounded gallery response; complete large-album browsing would require a separate pagination contract.

Public documents and private previews carry `galleryStatus`: `COMPLETE`, `PARTIAL` when eligible images are omitted, or `UNAVAILABLE` when gallery scanning or storage fails. The shared frontend gallery displays a generic notice for incomplete results even when no image is available. No hidden filenames or counts enter this status. Text remains readable during image-local failure; snapshot authorization and expiry still fail closed.

Each page preparation attempt processes at most 128 MiB of image bytes, giving body references priority over the gallery and charging each unique target once. Known Git sizes are checked before materialization. Managed reads reserve their 16 MiB maximum against this preparation budget and settle to actual bytes after success; failed reads retain their allowance. Targets that do not fit are omitted before reading. This bounds cumulative image preparation separately from concurrent-memory admission.

`GET /api/admin/workspaces/{workspaceId}/assets` and `…/assets/repository` supply bounded image pages. Multipart uploads require `Idempotency-Key`; private preview and image reads stay under `/api/admin/workspaces/{workspaceId}`. Public article responses supply media mappings and galleries, and `/api/public/assets/{token}` serves the exact granted bytes. Pages, RSS, sitemaps and Markdown HTML rendering belong to the frontend, not to these JSON and image APIs.

## Alternatives and related records

**Whole-commit validity.** The first snapshot served a commit only when every managed document in it was valid, so that it never presented a tree the owner had not committed. One malformed private file then hid every unrelated article. Per-file diagnostics keep unrelated articles available; publication-policy failure remains global because authorization cannot be guessed. The [phase-one delivery](2026-09-05-phase-one-daily-use.md#related-decisions-and-alternatives) records this reversal.

**Indefinite stale service.** Serving the last verified snapshot until the remote recovered maximized availability but could not bound the age of a public authorization decision. The snapshot lifetime bounds it at one hour.

**Revalidate the remote ref on each request.** A ref advertisement is cheaper than a fetch, but it still puts a remote round trip and every outage on the request path.

**Refresh from a provider push webhook.** The fixed delay works for every provider binding. A webhook could shorten the delay later without changing the freshness contract.

**Persist the parsed snapshot.** The cache already holds the objects, so the marker's commit and verification time are enough to rebuild the snapshot without a second serialized format.

**Load one blob per request instead of holding parsed articles.** Within the bounds above, memory for served content stays bounded by the workspace byte bound plus parsed overhead, and a lookup is a map read. A blob-per-request design can return if the bounds grow.

The [remote authority decision](2026-09-01-remote-repository-authority.md) owns the authority model; object-only reads and patches avoid worktree mutation and cleanup. The legacy UUID write stack of [document write operations](2026-08-29-document-write-operations.md) has no production caller and awaits removal. The shipped subset of the rejected [publishing proposal](../rejected/2026-09-01-repository-native-publishing-and-assets.md) is owned here.

## Verification and limits

`RepositoryHistoryDatesTests`, `PublicContentSnapshotTests`, `ContentSnapshotRefresherTests`, `RepositoryPatchServiceTests`, `RepositoryPatchIntegrationIT`, `PublicImagePreparationTests` and `AssetAuthorizationConcurrencyIT` pin these contracts through real Git objects and, for the integration tests, real PostgreSQL and Spring composition.

On Windows, `linuxStorageTest` is a required `check` dependency that replays the owning storage suites on a native Linux filesystem, including marker durability, snapshot restoration, the image-grant lifecycle and injected synchronization failures that must prevent a remote ref update; Linux CI runs them directly. They are synchronization and fault-order tests, not a simulated host power loss, and unsupported-platform tests do not substitute for them. The [isolated image-memory probe](../../acceptance/README.md) measures heap and container memory under maximum-size image work with real Linux services. Repository tree memory, workspace lock duration and total process native memory remain unmeasured limits.
